## 🤖 一、机器人描述文件：机器人的"DNA"（2.1 Robot Description Files）

### 1.1 为什么需要描述文件？

现代机器人工具的强大之处在于**通用性**——我们开发的算法可以轻松从一个机器人迁移到另一个。让这事成为可能的关键之一，就是**通用的机器人描述文件格式** 。

**生活类比**：就像乐高的说明书——它用标准格式告诉你"这个小人由哪几块积木组成、每块什么颜色、怎么拼"。机器人描述文件就是机器人的"乐高说明书"。

### 1.2 三种主流格式

Drake 目前支持 ：
- **URDF**（Unified Robot Description Format）——老牌格式
- **SDF**（Simulation Description Format）——功能更丰富
- **MJCF**（MuJoCo 格式）——有限支持

**现实情况**：这个领域还没统一（"the field has not converged on a single preferred format yet"），每种格式都有自己的怪癖 。

> 💡 Russ 的选择：Drake 开发团队致力于把改进**上游贡献给 SDF**，而不是再发明一种新格式。同时 Drake 提供了一个简单的 YAML 规范叫 **Drake Model Directives**，让你能非常快速地从不同文件格式中加载多个机器人/物体到一个仿真里——你其实在第1章的 notebook 里已经见过这个例子了。

### 1.3 为什么这事很重要？

**生活类比**：想象你要设计一个"万能遥控器"，但市面上的电视有的用红外、有的用蓝牙、有的用 WiFi——你得为每种协议写适配器。机器人描述文件格式不统一，就意味着每换一个机器人，算法就得改一遍。

Drake 的 Model Directives 就是那个"万能适配器"——一份 YAML 文件就能把 iiwa 机器人、WSG 夹爪、相机、桌子、物体全部组装起来。

## 🦾 二、机械臂：位置控制 vs 力矩控制（2.2 Arms）—— 全章最硬核部分

### 2.1 选臂的难题

市场上有大量机械臂可选。怎么选？成本、可靠性、易用性、负载、活动范围……考量因素很多。研究实验室的选择和创业公司的选择可能截然不同 。

Russ 直接给了一个**筛选利器**：

> "有一个特定的需求，如果我们希望机器人满足它，会迅速将候选范围缩小到仅少数几个可行平台：那就是**关节力矩感知与控制**。"

### 2.2 主角登场：KUKA LBR iiwa

在支持力矩控制的机器人中，Russ 在这些笔记里最常使用的是 **KUKA LBR iiwa**（他调侃说小写"iiwa"和厂商保持一致，但每次看着都觉得不对劲 ）。

为什么是 iiwa？因为 Russ 是研究机器人与世界**接触交互**的人，他**宁愿拥有力矩感知与控制的能力并探索是否需要它，也不愿去猜想'如果我有这能力会怎样'** 。

### 2.3 为什么大部分机器人是"位置控制"的？（2.2.1 Position-controlled robots）

这是本章**最精彩的物理数学课**。要理解它，先从电机的基本方程说起。

#### 电机的基本方程

对一台高质量的电机（绕组设计把转矩脉动降到最低），电机输出的转矩和施加的电流**直接成正比**：

$$\tau_{\text{motor}} = k_t i$$

其中 $\tau_{\text{motor}}$ 是电机转矩，$i$ 是电流，$k_t$ 是电机转矩常数。

**同理，施加的电压与电机的稳态速度之间也存在简单的（仿射）关系**。

> 💡 既然电流和转矩成正比，**那我们直接控制电流，不就等于控制转矩了吗？** 为什么市面上大部分机器人做不到真正的力矩控制？

#### 减速器的"罪魁祸首"

简短的答案是：**为了实现合理的成本和重量，我们通常会选择小电机 + 大减速比**。而减速器带来了一系列**极难建模的动态效应**——包括**齿隙（backlash）、振动（vibration）、摩擦（friction）** 。

**生活类比**：想象你在拧一瓶矿泉水。你用手指直接捏瓶子（直驱），你用的力和瓶子受到的压力是 1:1 的关系，你能精确控制。但现在想象你戴了一副超厚的、松松垮垮的橡胶手套去拧——你的手在动，但瓶子感受的力被手套的松弛、摩擦、变形"污染"了。你用的力和瓶子实际受到的力**不再是简单的正比关系**。

**核心结论**：

> "传统观点认为，对于大减速比（比如 ≫ 10），未建模项的影响足够显著，不能被忽略，转矩不再与电流简单相关。"

#### 位置控制的救场方案

既然我们没有传动动力学的好模型，怎么克服这个挑战？

**关键观察**：
- 调节电机侧的速度/电流**只需要电机侧的传感器**
- 但要精确调节关节，**我们通常需要在传动的输出侧添加更多传感器**

**最重要的是**：尽管传动带来的转矩不精确，但它们**并非任意的**——比如它们绝不会给系统注入能量。而且我们可以确信：**输入电机的电流与关节处的转矩、进而与关节加速度之间，存在单调递增关系**。

> 💡 "单调（monotonic）"这个词 Russ 选得很谨慎——意思是"非递减"，但不意味着"严格递增"。因为当关节从静止启动时，**静摩擦会抵抗小的转矩，而输出没有任何加速度**。

#### PID 控制的数学

在关节上添加的最常见传感器是**位置传感器**（通常是编码器或电位计）——它们便宜、精确、鲁棒。在实践中，我们认为这些传感器（经过信号滤波/调理后）能提供**精确**的关节位置和速度测量。关节加速度也可以通过二次微分获得，但通常被认为噪声较大，不适合用在紧凑的反馈回路中。

位置传感器足以精确跟踪手臂的期望位置轨迹。对于每个关节，记关节位置为 $q$，给定期望轨迹 $q^d(t)$，我们可以用 **PID 控制**来跟踪：

$$\tau = k_p(q^d - q) + k_d(\dot{q}^d - \dot{q}) + k_i\int(q^d - q)dt$$

其中 $k_p, k_d, k_i$ 分别是比例、微分、积分增益 。

**生活类比**：
- **P（比例）**：你现在的位置和目标的差距有多大 → 差距越大，出力越大（像弹簧）
- **D（微分）**：你正在以多快速度接近目标 → 快到了就提前减速，防止冲过头（像阻尼器）
- **I（积分）**：过去的误差累积了多少 → 如果一直差一点点，慢慢加码消除稳态误差（像记忆）

> ⚠️ **Russ 的实战提醒**：当我们在仿真位置控制机器人时，往往需要**对物理机器人和仿真使用不同的增益**。这是因为传动动力学，而且硬件上的 PID 控制器通常输出的是**电压命令（通过脉宽调制）**，而非电流命令。缩小这个建模差距传统上不是机器人仿真的主要优先级——因为还有其他更多细节主导着"仿真到现实"的鸿沟——但 Russ 怀疑随着领域成熟，主流机器人仿真器最终也会捕捉这一点 。

#### 对"神经网络建模"的乐观态度

有些同学会想："我可以训练神经网络来建模任何东西，我不怕难以建模的传动！"

Russ 认为这种思路有理由乐观——已经有初步的演示（如 Hwangbo 等人 2019 年的工作 ）。虽然这不如"用第一性原理模型从描述文件中的几个参数推广到新执行器"那么有用，但可能是非常有成效的方向。

### 2.4 传动中的连杆动力学（An aside: link dynamics with a transmission）—— 反射惯量的奥秘

这一节是**本章数学含量最高的部分**，但 Russ 用了一个非常漂亮的推导，揭示了为什么大减速比让控制变得"意外地简单"。

#### 电机的高效工作区

电动电机在高速时效率最高（通常 >100 或 1000 RPM）。但我们其实**不希望**机器人动得那么快！所以几乎所有的电动机器人都有**相当大的减速比，通常在 100:1 左右**——传动输出每转一圈，电机转 100 圈，输出转矩是电机转矩的 100 倍 。

对于驱动关节 $q$ 的减速比 $n$，我们有：

$$q_{\text{motor}} = n q, \quad \dot{q}_{\text{motor}} = n\dot{q}, \quad \ddot{q}_{\text{motor}} = n\ddot{q}, \quad \tau_{\text{motor}} = \frac{1}{n}\tau$$

#### 关节动力学方程

先写关节转矩和关节加速度的关系（还没引入电机）：

$$I_{\text{arm}}\ddot{q} = \tau_{\text{gravity}} + \tau$$

其中 $I_{\text{arm}}$ 是转动惯量。例如，对于一个简单单摆：

$$ml^2\ddot{q} = -mgl\sin q + \tau$$

#### 转换到电机坐标系

但实际施加的关节转矩 $\tau$ 来自电机——如果我们用电机坐标系写这个方程：

$$\frac{I_{\text{arm}}}{n}\ddot{q}_{\text{motor}} = \tau_{\text{gravity}} + n\tau_{\text{motor}}$$

两边除以 $n$，并考虑电机本身也有惯量（比如大磁铁旋转带来的惯量），它不受减速比影响：

$$\left(I_{\text{motor}} + \frac{I_{\text{arm}}}{n^2}\right)\ddot{q}_{\text{motor}} = \frac{\tau_{\text{gravity}}}{n} + \tau_{\text{motor}}$$

#### 反射惯量的概念

这里出现了一个非常有趣的现象：

> "我们用具术语**反射惯量（reflected inertia）**来表示传动另一侧由于传动的缩放效应而感受到的惯性负载。手臂在电机侧的'反射惯量'被减速比的平方削减；或者说，电机在手臂侧的'反射惯量'被减速比的平方放大。"

**生活类比**：想象你在自行车的踏板端（电机侧）感受后轮的惯性。因为齿轮比的存在，后轮的重物在踏板端"感觉"轻了齿轮比平方的倍数——这就是反射惯量。反过来，你在后轮端感受踏板的轻——踏板的小质量在后轮端"感觉"重了齿轮比平方的倍数。

#### 大减速比的"魔法效应"

对于大减速比：
- $I_{\text{motor}}$ 项**主导**其他项
- 这带来两个重要影响 ：
  1. **它有效地对角化了机械臂方程**（惯性耦合项相对较小）
  2. **动力学在整个工作空间内相对恒定**（状态相关项相对较小）

**这就是为什么给每个关节独立整定恒定的反馈增益，就能在所有配置下都表现良好**——尽管机械臂的关节动力学是高度耦合且与状态相关的！

> 💡 **工程启示**：大减速比虽然让"电流→转矩"的关系模糊了，但却意外地**简化了控制问题**——让我们可以简单地对每个关节用独立的 PID，而且增益可以恒定不变。这是机器人学里一个非常反直觉又极其实用的洞见。

### 2.5 力矩控制机器人（2.2.2 Torque-controlled robots）

虽然不那么常见，但有一些机器人确实支持关节转矩的直接控制。有几种实现方式：

#### 方式一：小减速比/直驱

使用**只需要小减速比（例如 ≤ 10:1）的电机**，此时摩擦力可忽略。

- **过去**："直驱机器人"（Asada & Youcef-Toumi, 1987）有巨大的电机和有限的负载
- **近期**：Barrett WAM 机械臂用缆绳传动，把大电机放在基座，保持臂轻
- **最近几年**：高转矩外转子电机和无框电机带来了新一代低成本、"准直驱"机器人：**MIT Cheetah、Berkeley Blue、Halodi Eve** 

#### 方式二：液压执行器

液压执行器提供了另一种无需大传动就能产生大力矩的方案。Sarcos 有一系列力矩控制臂（和人形机器人），波士顿动力的许多著名机器人基于液压（尽管近年有向电机转变的趋势）。这些机器人通常有一个中央泵，每个执行器有一个（轻量）阀，可以分流流体通过执行器或旁路；执行器两端的压差至少近似与产生的力/转矩相关。

#### 方式三：大减速比 + 关节侧力矩传感器（iiwa 的方式）⭐

**保留大减速比电机，但在执行器关节侧添加传感器直接测量力矩**。这就是我们全文使用的 KUKA iiwa 采用的方法——iiwa 执行器在传动中集成了应变片 。

**刚度与精度的权衡**：

> "然而，传动的刚度与力/力矩测量的精度之间存在权衡。"

iiwa 传动包含一个显式的"**柔性花键（Flex Spline）**"，刚度大约为 **5000 Nm/rad** 。

**极端化这个想法**：Gill Pratt 提出了"**串联弹性执行器（Series-Elastic Actuators）**"，在传动中具有更低刚度的弹簧，并提出在传动的电机侧和关节侧都测量关节位置，以估计施加的转矩 。例如，Rethink 的 Baxter 和 Sawyer 机器人使用了串联弹性执行器；Russ 认为它们从未公布弹簧刚度值，但受类似动机驱动的 HEBI 机器人学的串联弹性执行器更接近 100 Nm/rad。

**即使是 iiwa 执行器，关节弹性也显著到其底层控制器必须不遗余力地显式考虑它，以实现关节的高性能控制**（Albu-Schaffer et al., 2007）。这件事我们会在讲到力控制的那一章详细讨论。

### 2.6 硬件的普及化（2.2.3 A proliferation of hardware）

Russ 兴奋地指出：上面提到的低成本力矩控制臂，仅仅是**承诺中的大规模机器人臂普及浪潮的开始**。疫情期间，Russ 看到很多人在家里使用像 xArm 这样的廉价机器人。随着需求增加，成本将继续下降。

**Russ 的感慨**：

> "让我直言：与做腿式机器人研究相比——几十年来我们在研究生（偶尔是教授！）在走廊尽头的机器车间里建造的实验室原型上做研究——能用到专业工程化、高质量、高正常运行时间的硬件，绝对是一种享受。"

这意味着：
- 我们可以在一个实验室测试算法，另一个大学实验室在几乎相同的硬件上测试算法
- 这促进了以前不可能的**可重复性和共享水平**
- 价格下降意味着更多实验室/环境中会有更多相似机器人

**Russ 的乐观预言**：

> "这是一个做操作研究的好时代！"

## 🔧 三、仿真 KUKA iiwa（2.2.4 Simulating the Kuka iiwa）

### 3.1 第一步：获取机器人描述文件

首先是获取机器人描述文件（通常是 URDF 或 SDF）。为了方便，Drake 自带了包括 iiwa 在内的几个机器人的模型。如果你想仿真不同的机器人，可以在网上找到大多数商用机器人的 URDF 或 SDF。

> ⚠️ **Russ 的警告**：这些模型的质量**差异巨大**。我们甚至在运动学（连杆长度、几何形状等）上也看到过令人惊讶的错误，而动力学属性（惯量、摩擦等）尤其经常完全不准确。有时它们甚至在数学上不一致（例如，有可能在 URDF/SDF 中指定一个刚体无法实现的惯性矩阵）。**Drake 会抱怨**如果你让它加载有这种违规的文件；我们宁愿及早提醒你，而不是开始生成虚假的仿真。现在也有越来越好的支持，可以直接从 SolidWorks 等 CAD 软件导出机器人格式。

### 3.2 第二步：导入物理引擎

在 Drake 中，物理引擎叫 **MultibodyPlant**。"plant"这个词可能看起来奇怪，但它无处不在；它是控制文献中用来表示"要控制的物理系统"的词，起源于化工 plant 的控制。这种与控制理论的联系对 Russ 非常重要。**世界上没有多少物理引擎像 Drake 这样竭尽全力地使物理引擎与控制理论设计和分析兼容**。

MultibodyPlant 有一个类接口，带有丰富的库方法，用于处理机器人的运动学和动力学。如果你需要计算质心位置、运动学雅可比矩阵或任何类似的查询，你都会使用这个类接口。MultibodyPlant 也实现了在 Drake 系统框架中作为 System 使用的接口，带有输入和输出端口。为了仿真或分析 MultibodyPlant 与其他系统（如我们的感知、规划、控制系统）的组合，我们将组装框图。

#### MultibodyPlant 的端口

作为一个复杂而通用的物理引擎，它有许多输入和输出端口；大多数是可选的：

```
applied_generalized_force →  → continuous_state
applied_spatial_force →      → body_poses
model_instance_name[i]_actuation →  → body_spatial_velocities
                              →  → body_spatial_accelerations
geometry_query →             →  → generalized_acceleration
                              →  → reaction_forces
                              →  → contact_results
                              →  → model_instance_name[i]_continuous_state
                              →  → model_instance_name[i]_generalized_acceleration
                              →  → model_instance_name[i]_generalized_contact_geometry_pose
```

### 3.3 🧪 实验重点：Example 2.2（仿真被动 iiwa）

> "值得花几分钟时间在这个例子上，它应该能帮助你理解物理引擎，以及用 Drake 做仿真的一些基本机制。"

**实践要点**：
1. 点击 "Launch in Deepnote" 运行这个例子
2. **观察关键现象**：我们施加零转矩，机器人**掉下去了**（falls down）
3. 在现实中这永远不会发生——事实上，即使控制器关闭，物理 iiwa 机器人在关节处也几乎不会经历零转矩。像许多成熟的工业机械臂一样，iiwa 在每个关节都有机械刹车，在控制器关闭时啮合。要仿真控制器关闭的机器人，我们需要告诉物理引擎这些刹车产生的转矩。
4. 即使控制器开启，尽管它是力矩控制机器人，我们也永远无法实际向电机发送零转矩。iiwa 软件接口接受"前馈转矩"命令，但它总是将这些作为附加转矩加到其底层控制器上，底层控制器在补偿重力和电机/传动机械。

**🎯 关键学习点**：
- **最简单的合理 iiwa 仿真必须包含 Kuka 底层控制器的仿真**
- 我们将使用 iiwa 的"关节阻抗控制"模式
- 目前我们可以将其视为给定的，并生成我们最简单的合理 iiwa 仿真
- 这些细节会在我们为了让机器人表现更好而变得重要时描述

### 3.4 🧪 实验重点：Example 2.3（可视化场景）

> "这个例子观看要有趣得多。现在我们有了 3D 可视化！"

**为什么 MultibodyPlant 不处理场景几何？**

你可能会想，为什么 MultibodyPlant 不也处理场景的几何。嗯，有许多应用我们希望渲染复杂场景并使用复杂传感器，但提供自定义动力学而不是使用默认物理引擎。自动驾驶就是一个很好的例子；在这种情况下，我们希望用车辆和环境的几何填充 SceneGraph，但我们通常希望用非常简单的车辆模型仿真车辆，远不至于把轮胎力学加入物理引擎。在我的《Underactuated Robotics》课程中，我们也有许多这种工作流程的例子，我们广泛使用"简单模型"。

**实践要点**：添加 SceneGraph 系统来策划场景几何，然后添加可视化器和传感器来实际渲染场景。

### 3.5 运动学仿真 vs 动力学仿真

Russ 提出一个有趣的观点：

> "作为最后的说明，你可能会认为仿真机器人动力学是过度的，如果我们唯一的目标是仿真操作任务，其中机器人只相对缓慢地移动，质量、惯量和力的影响可能不如机器人和物体在空间中的位置那么重要。我实际上会同意你。但让运动学仿真遵守交互的基本规则出奇地棘手；例如，知道物体何时被捡起何时没有（参见例如 Pang 和 Tedrake 的工作）。目前，在 Drake 中，我们主要使用完整的物理引擎做仿真，但经常使用更简单的模型进行操作规划和控制。"

## ✋ 四、手（末端执行器）：三大门派（2.3 Hands）

你或许注意到了，iiwa 模型实际上**没有附带手**——机器人出厂时带有一个安装板，以便你可以安装你选择的"末端执行器"。所以我们需要决定：用什么手？

有趣的是，在操作研究中，研究人员倾向于分成几个不同的阵营。

### 4.1 灵巧手阵营（2.3.1 Dexterous hands）

当然，我们对人手着迷是有道理的，我们梦想构建同样灵巧且富含传感器的机械手。但现实是我们还没到那一步。

**OpenAI 的著名"学习灵巧性"项目**用了 Shadow 手玩魔方，为了让手支持耐力学习实验，对手本身所做的工作绝对是故事的一部分。

**希望**：新的制造技术可能真正颠覆这个领域——FLLEX v2 这样的视频看起来惊人。Russ 非常乐观，认为在不久的将来我们会拥有更有能力、更鲁棒的灵巧手。

### 4.2 简单夹爪阵营（2.3.2 Simple grippers）⭐ 本课的选择

另一个阵营指出灵巧手是不必要的——我从玩具店给你一个简单的夹爪，你仍然可以在家中完成惊人有用的任务。上面的 PR1 视频就是很好的证明。

**支持简单手的另一个重要论点**：**降低复杂性带来的优雅和清晰**。如果清晰地思考简单夹爪能帮助我们更深入地理解为什么我们需要更灵巧的手（Russ 认为是的），那就太好了。

**本课的选择**：**Schunk WSG 050**——我们在过去几年的研究中广泛使用了它。

> 💡 **重要澄清**：简单（少自由度）不等于低质量。**相反，Schunk WSG 是一个非常高质量的夹爪，其单一自由度的力控制和力测量精度超越了 Kuka**。在具有许多关节的灵巧手上实现同样的性能是非常困难的。

### 4.3 软体/欠驱动手阵营（2.3.3 Soft/underactuated hands）

最后，第三也是最新的阵营正在推广聪明的机械设计手，通常称为"**欠驱动手（underactuated hands）**"。

**基本思想**：对于许多任务，你可能不需要手中执行器数量和关节数量一样多。许多欠驱动手使用缆绳传动机制来闭合手指，其中单个肌腱可以导致手指中的多个关节弯曲。

**生活类比**：这就像你握门把手——你只需要收缩前臂的一组肌肉（一个执行器），你的手指就会自然地围绕门把手的形状弯曲包裹。你没有单独控制每根手指的每个关节，但你的手**被动地**适应了门把手的形状。

**当正确设计时**，这些机制允许手指**被动地顺应**被抓物体的形状，而无需改变执行器命令。

**极端化**：近年来也出现了许多完全软体的手（或至少手指）。"软体机器人社区"正在迅速改变机器人制造的技术水平，具有可以完全软的附属肢体、执行器、传感器甚至电源。

**欠驱动手的优缺点**：
- ✅ 往往是某些范围任务的极佳例子（最常见的是"包络抓取"）
- ❌ 但不是通用的——很难用它们来扣衬衫纽扣
- 但它们正变得越来越灵巧

### 4.4 其他末端执行器（2.3.4 Other end effectors）

不是所有末端执行器都需要像灵巧手或简化人手那样操作。

**真空吸盘（Suction-cup grippers）**：
- 当今许多工业应用使用真空吸盘做某种形式的 pick-and-place
- 在许多但并非所有物体上效果极好
- 有些物体太软或多孔，无法有效吸附
- 有些物体太脆或太重，无法从顶部真空抬起，必须从下方支撑
- 有些手在手掌有吸盘以实现初始拾取，但仍使用更传统的手指来稳定抓取

**阻塞夹爪（Jamming gripper）**：

> Russell 最喜欢的一个：这些夹爪由一个装满咖啡渣或其他颗粒介质的球囊组成；将球囊压在物体周围允许颗粒介质在物体周围流动，然后对球囊施加真空导致颗粒介质"阻塞"，快速硬化在物体周围以形成稳定抓取。

**带驱动滚轮的夹爪**：在指尖有驱动滚轮帮助手内重新定向。

**工具快换装置（Tool changer）**：

Matt Mason（多年来简单夹爪的主要倡导者之一）在机器人研讨会结束时对一个问题的回答特别有意思：他认为，例如在厨房的有用机器人可能会有可以快速更换的专用工具。**在灵巧手的主要工作是更换工具的应用中，我们可以通过在机器人上直接安装"工具快换装置"并使用兼容工具快换的工具，来跳过复杂性。**

### 4.5 如果你还没见过（2.3.5 If you haven't seen it...）

Russ 分享了他最喜欢的机器人：Ishikawa 组的"高速多指手"项目——2004 年开始产出惊人结果！他们"超频"了手（在短时间内发送比任何长时间应用都合理的更大电流），并使用高速相机来实现这些结果。他们在 2017 年也有一个魔方演示。

## 🏗️ 六、整合：HardwareStation（2.5 Putting It All Together）

如果你已经完成了这些例子，你会看到我们机器人的合理仿真不仅仅是物理引擎——它需要**将物理、执行器和传感器模型以及底层机器人控制器组装到一个通用框架中**。在 Drake 中，这意味着我们正在组装越来越复杂的框图。

### 6.1 HardwareStation 的诞生（2.5.1 HardwareStation）

框图建模范式最好的事情之一是抽象和封装的力量。我们可以组装一个 Diagram，其中包含仿真我们的硬件平台及其环境所需的所有组件，我们亲切地称之为"**Hardware Station**"。

`MakeHardwareStation` 方法接受一个描述场景和机器人硬件的 **YAML 描述**。

#### HardwareStation 的端口

对于一个描述 iiwa + WSG 和一些相机的 YAML 文件，生成的 HardwareStation 系统看起来像这样：

**输入端口**（橙色"作弊端口"只在仿真中可用）：
```
iiwa.position (可选，非 position_only 模式时)
iiwa.torque (可选，非 torque_only 模式时)
wsg.position
wsg.force_limit (可选)
```

**输出端口**：
```
→ iiwa.position_commanded
→ iiwa.position_measured
→ iiwa.velocity_estimated
→ iiwa.state_estimated
→ iiwa.torque_commanded
→ iiwa.torque_measured
→ iiwa.torque_external
→ wsg.state_measured
→ wsg.force_measured
→ camera_[NAME].rgb_image
→ camera_[NAME].depth_image
→ camera_[NAME].label_image
→ ...（更多相机）
→ query_object
→ contact_results
→ plant_continuous_state
→ body_poses
```

> 🎨 **橙色的输出端口是"作弊端口"**——它们在仿真中可用，但在真实机器人上运行时不可用（因为它们假定了真值知识）。

### 6.3 🧪 实验重点：Example 2.7（双手操作站）

> "通过在 YAML 文件中添加几行，我们可以使用相同的 MakeHardwareStation 方法构建双手站"

### 6.4 HardwareStationInterface（2.5.2 HardwareStationInterface）

如你在例子中看到的，HardwareStation 框图本身旨在用作额外框图中的 System，这可以包括我们的感知、规划和更上层的控制系统。这个模型也定义了仿真和真实硬件之间的抽象。

通过简单地向 MakeHardwareStation 方法传递 `hardware=True`，我们转而构建一个几乎相同的系统，**HardwareStationInterface**。

HardwareStationInterface 也是一个框图，但不是由 MultibodyPlant 和 SceneGraph 等仿真组件组成，而是由执行**网络通信**以与各个硬件驱动程序对话的小型可执行文件交互的系统组成。

**为什么用 LCM 而不是 ROS**？

如果你深入底层，你会看到我们使用 **LCM** 而不是 ROS 消息，主要是因为 LCM 对我们的公共仓库是更轻量级的依赖（也因为多播 UDP 是驱动级接口的 TCP/IP 的更好选择）。但许多 Drake 开发者/用户也在 ROS/ROS2 生态系统中使用 Drake。

### 6.5 独立硬件仿真（2.5.3 HardwareStation stand-alone simulation）

使用 HardwareStation 工作流，从仿真开发过渡到真实机器人上运行非常容易。支持这个工作流的另一个工具是独立的 `hardware_sim` 可执行文件。

这个 python 脚本接受相同的 YAML 文件作为输入（通过命令行），并在一个**单独的进程**中启动仿真，该进程的行为就像真实机器人硬件应该的那样……发送和接收硬件侧的消息。这对于测试你的所有逻辑在消息传递层添加一些延迟和非确定性时是否仍然工作非常有价值——而我们在开发的第一阶段使用 `MakeHardwareStation(..., hardware=False)` 时巧妙地避免了这些。

```bash
python3 drake/examples/hardware_sim/hardware_sim.py \
  --scenario_file=station.yaml \
  --scenario_name=Name
```

在这个练习中，你将研究反射惯量对机器人关节空间动力学的影响，以及它如何影响简单的位置控制律。你将完全在这个 notebook 中工作。

**b. 比较在相同位置控制律下，直驱简单单摆和高减速比齿轮箱简单单摆的行为**

> 💡 **实验重点**：这是本章**最硬核的数学练习**。
>
> **具体步骤**：
> 1. 从单摆的转动方程出发：$I_{\text{arm}}\ddot{q} = -mgl\sin q + \tau$
> 2. 引入电机和减速比 $n$，转换到电机坐标系
> 3. 推导状态空间形式：$\dot{x} = f(x, u)$

> 💡 **实验重点**：从第1章的"滑块控制末端执行器（笛卡尔空间）"升级到"直接控制关节角度（关节空间）"。

### Exercise 2.4：Drake 中的 PID 控制（🔧 代码重点）

在这个练习中，你将实现 Drake 中机器人关节的 PID 控制器。你将完全在这个 notebook 中工作。

**a. 为机器人关节实现 PD 控制器**
**b. 将 PD 控制器扩展为完整的 PID 控制器**

> 💡 **实验重点**：这是你**第一次在 Drake 中从零实现 PID 控制器**。
>
> **Drake 的 PidController 类**：
> ```cpp
> // 给定估计状态 x_in = (q_in, v_in)，
> // 受控状态 x_c = (q_c, v_c) 由 x_c = P_x * x_in 计算
> // 期望状态 x_d = (q_d, v_d) 与 x_c 在同一空间
> // 控制器输出为：
> // y = P_y * (kp * (q_d - q_c) + kd * (v_d - v_c) + ki * integral(q_d - q_c))
> ```
>
> **具体步骤**：
> 1. 实现 PD 控制器：$\tau = k_p(q^d - q) + k_d(\dot{q}^d - \dot{q})$
> 2. 测试：给一个阶跃目标，观察响应
> 3. 调增益：先调 $k_p$ 直到响应快速且无过大超调，再调 $k_d$ 抑制振荡，最后加 $k_i$ 消除稳态误差
> 4. 扩展为完整 PID：加入积分项
> 5. **关键观察**：你会发现关节空间的 PID 控制**非常有效**——这验证了 Russ 在 2.2.1 节讲的"大减速比让控制问题意外简化"
>
> **生活类比**：调 PID 增益就像调音响的均衡器——
> - 只加 $k_p$：低音太重，声音轰鸣（震荡）
> - 加 $k_d$：高音上来，抑制了轰鸣（阻尼）
> - 加 $k_i$：中音饱满，消除了细微失真（稳态误差）
